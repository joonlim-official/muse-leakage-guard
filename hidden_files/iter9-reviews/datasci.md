## 1. Confirmed by execution

### 1.1 [P1] Findings-section replay re-emits `@@@ CTX` sentinels → card E contamination, terminal sentinel leak — NEW
- **Files/lines:** `bin/leakage-audit:155` (`wdetail` emits `msent "CTX $line"`),
  `bin/leakage-audit:168,171,175` (`bad()` appends `$(… | wdetail)` output to `FINDINGS`),
  `bin/leakage-audit:~330` (`print_summary` re-emits `$FINDINGS` in the Findings section),
  `bin/leakage-report:90` (`parse_machine` treats any `CTX` line as current-suite evidence).
- **Issue:** `wdetail` is dual-purpose: human formatting *and* machine-sentinel
  emission. `bad()` captures `wdetail`'s stdout — including the re-emitted
  `@@@ CTX` lines — into `$FINDINGS`. When `print_summary` later replays the
  Findings section, those stored `@@@ CTX` lines are emitted again. Any consumer
  reading the Findings section as machine data (the report's `parse_machine`
  with `suite="E"`) attributes the replayed lines as evidence of suite E.
- **Execution proof:** In a `/tmp` copy, broke the stub's blockset so one
  suite-A check failed. Terminal Findings section contained raw
  `@@@ CTX    1. Suggestion: run: build/build-blockset.sh` lines. The HTML
  report's card E ("Known gaps") rendered "Operational notes: … Suggestion:
  run: build/build-blockset.sh — or remove the check" under the residuals —
  a suite-A remediation displayed as if it were gap documentation.
  (`bin/leakage-audit:330` is where the Findings section is replayed; the
  audit still exits 1 correctly — the verdict is unaffected, the evidence
  attribution is wrong.)
- **Impact:** On a red run — exactly when the report is needed for
  diagnosis — readers of card E see another suite's remediation notes
  misfiled as residual-gap documentation. Terminal users with
  `MOCHI_AUDIT_MACHINE=1` see raw sentinels in human-readable output.
  This survived Iteration 8's "report integrity" theme (the `CTX` emission
  dates to Iteration 3, commit `93d1990`; the `FINDINGS` capture to an older
  "every failure now carries a suggested remediation" commit).
- **Remediation:** Do not capture sentinel-emitting output into `FINDINGS`.
  Emit machine sentinels only during original check execution; when replaying
  findings, either strip `@@@` lines or store typed evidence separately
  (e.g. an associative array of suggestion→check) and render fresh at
  summary time. Add a regression test: forced-red run → assert no `@@@`
  lines inside the Findings section and no `CTX` attributed to suite E.
- **Status:** confirmed by execution.

### 1.2 [P2] Report timestamps are wrong on non-UTC machines — NEW
- **File/lines:** `bin/leakage-report:241-251` (`fmt_ts`).
- **Issue:** The audit emits `run-started: 2026-09-17 17:24 PDT`. `fmt_ts`
  regexes `\(([^)]+)\)`, takes the wall-clock `2026-09-17 17:24`, and
  forcibly attaches `tzinfo=timezone.utc`, displaying `2026-09-17 10:24 AM
  PDT (2026-09-17 17:24 UTC)`. It discards the supplied zone instead of
  parsing it, so the local time is off by the UTC offset.
- **Execution proof:** With `TZ=America/Los_Angeles`, audit emitted
  `2026-09-17 17:24 PDT`; the generated HTML displayed
  `2026-09-17 10:24 AM PDT` — 7 hours early (correct value: 5:24 PM PDT).
- **Impact:** Every report generated by the owner (America/Los_Angeles) shows
  a run time 7–8 hours wrong. A timestamp that is systematically wrong is
  worse than none — it can mislead incident correlation (e.g. "when did the
  gate log entry happen relative to the audit run").
- **Remediation:** Emit ISO-8601 with a numeric offset (or epoch seconds)
  from the audit; in the report, parse the offset and convert, rather than
  replacing it. The "local time shown with UTC original" claim in the
  Iteration 8 CHANGELOG is currently false outside UTC — re-verify after fix.
- **Status:** confirmed by execution.

### 1.4 [P2] Vacuous tiers pass: an emptied contract tier still reports green — re-confirmed (iter8 P1-4)

### 1.5 [P2] Duplicate corpus names inflate denominators and tighten CIs — re-confirmed (iter8 P2-3)

### 1.7 [P2] Suite D passes on an empty gate log — "review" without evidence — NEW

  verdict), recency, target identity, malformed-line rejection, linkage to

  fails; require at least one decision entry since the last audit for the
  current target before claiming "reviewed". Qualify test-matrix.md:76.
- **Status:** confirmed by execution.

## 3. Methodology notes (labels as ground truth)

### 3.1 [P1] Stub block-tier 19/19 is reconstruction, not independent validation — acknowledged, still the ceiling
`build/build-blockset.sh` derives block tokens from the corpus's own
`want=1` rows, and the stub's detector classifies by lookup in that set.
The corpus is simultaneously the training set and the test set. The docs
(stub README, report "Stub consistency" callout) are honest about this —
the number measures harness self-consistency, not detection quality. The
risk is external: any consumer quoting "36/36" without the "stub" qualifier
overclaims. Remediation: an independently authored holdout set (labels
adjudicated separately from the corpus authors) or a big-print
"SELF-CONSISTENCY ONLY" watermark on the F card. Static analysis.

### 3.2 [P2] `clean_price|2` bakes a policy label the corpus can't defend
`bin/adversarial-corpus.txt`: `clean_price|2` ("the new GPU costs $12,500")
*expects* approval-gating, while `references/gate-interface.md` E1 says
public information is never gated. The stub passes because its figure
pattern has no public-info exemption — i.e., the corpus *punishes* the
behavior E1 requires. The `.egress-allowlist` mechanism that would resolve
this is referenced in a suggestion string (`bin/leakage-audit:417`) and
docs but is implemented nowhere in the stub and exercised by no test
(2.1). Labels are author assertions with no adjudication trail, provenance,
or disputed-label state (iter8 P1-2, P1-3 — still open: zero `KNOWN-GAP`
markers exist in the repo). Remediation: give every label a rationale +
provenance field, an adjudication workflow, and a `DISPUTED` state; test
the allowlist path end-to-end. Static analysis.

### 3.3 [P2] Clopper–Pearson lower bounds on an author-designed fixture set
The arithmetic is verified correct (19/19 → ≥0.82, 9/9 → ≥0.66, 8/8 →
≥0.63 — recomputed independently). The issue is inferential framing on a
non-random instrument: the corpus is a hand-built regression set, not a
sample from a population, so "worst case consistent with these results"
has no sampling basis for real-world detector performance. Iteration 8
replaced the unexplained label with the plainer "Worst case consistent with
these results (95% lower bound)", which is clearer prose but the same
inference. Remediation: label these as hypothetical Bernoulli-model
sensitivity ("if these were i.i.d. Bernoulli trials…") or drop the
