## Findings

### P0 — Report green conflates blocked and approval-gated; the brief's tri-state semantics are invisible

- **Priority:** P0
- **Title:** Green conflates "blocked" and "refused-without-approval"; yellow never means "protected through approval"
- **Evidence:** The brief defines the product semantics as green = well
  protected, yellow = protected through approval, red = can leak. In the
  report, the Gate effectiveness card reads "🟢 Gate effectiveness: 29 of
  29 green," yet its evidence includes approval-gated checks rendered as
  green ✓ rows: "gmail +send figure refused w/o approval (rc=2
  invoked=0)", "drive permissions create refused w/o approval (rc=2
  invoked=0)". Meanwhile the only yellow in the report is the "🟡 Known
  residuals: 4 known paths reported and tracked — none silent" card —
  which is actually good news (transparent tracking), not "protected
  through approval." A non-expert reading "29 of 29 green" concludes
  "nothing can leak"; the approval-gated paths — the ones that *can*
  leak with approval, by design — are buried as undifferentiated green.
- **Recommendation:** Make the tri-state visible. Either split the Gate
  effectiveness card into block-tier and review-tier callouts (green for
  hard-blocked, yellow for approval-gated with an explicit "leaks only
  with the owner's explicit approval" caption), or tag each rc=2 check
  with a distinct marker. Reserve yellow for the brief's defined meaning,
  not for the residuals card (recolor residuals to neutral/info).

### P0 — Five colors, no legend; the strongest caveat wears the weakest color

- **Priority:** P0
- **Evidence:** `callout()` in `bin/leakage-report` (lines 215–238) uses
  🟢 🟡 🔴 for suites, 🔵 ("Stub consistency") for the stub F-card, and
  ⚪ ("no checks ran — treat as unknown") for the no-data case. The HTML
  contains no legend — `grep` for legend/color-key in the generator
  returns nothing. A reader scanning within 30 seconds must infer five
  color meanings, and the inference is wrong where it matters most: ⚪
  "treat as unknown" is the strongest warning in the system but the least
  visually alarming; 🟡 reads as a warning but means "we track this
  openly." The stub-blue 🔵 is a fourth traffic-light entry with no
  explanation of how it relates to green/yellow/red.
- **Recommendation:** Add a one-line legend directly under the hero
  (e.g. "🟢 protected · 🟡 protected through approval · 🔴 can leak ·
  🔵 stub self-check, not protection · ⚪ unknown — do not trust").
  Treat ⚪/UNKNOWN as a hard failure visually (red-adjacent), since the
  report already refuses to write HTML on unparseable output — an
  "unknown" card that renders calmly contradicts that discipline.

### P1 — Stub card still speaks detector-quality vocabulary ("recall", "precision")

- **Priority:** P1
- **Evidence:** For stub targets the F-card h2 is honest ("🔵 Stub
  consistency: 36/36 corpus cases matched expected verdicts against the
  synthetic test double — harness self-check, not detector validation,"
  line 224). But the card's tier line (`cases_html`) still renders
  "block-tier recall 19/19 · review-tier recall 9/9 · clean precision
  8/8" — detector-quality vocabulary. The stub's detector classifies by
  lookup in `bin/blockset.txt`, which is *derived from the same corpus*
  (`build/build-blockset.sh` builds block-tier tokens from corpus want=1
  cases + declared fixtures), so stub block-tier "recall" is largely
  tautological. A reader who skips the h2 sentence and reads the tier
  line takes away "19/19 recall" as a quality claim.
- **Recommendation:** For stub targets, relabel the tier line in
  self-consistency vocabulary (e.g. "self-consistency 19/19 block-shape
  fixtures · 9/9 review-shape · 8/8 clean-shape") and carry the two
  by-design corpus exceptions (below) as annotations on their table rows,
  so the per-case table cannot be screenshotted as a detector scorecard.

### P1 — 19/19, 9/9, 8/8 are corpus fixtures, not real-world detection — the report's ML vocabulary overclaims

- **Priority:** P1
- **Evidence:** `bin/adversarial-run`'s own header comment is careful
  ("'clean precision' is the clean-class pass rate, not the ML precision
  of the block class"), but the report card presents "block-tier recall
  19/19, review-tier recall 9/9, clean precision 8/8" with no caveat that
  these measure a fixed 36-fixture corpus (verified: 19 want=1, 9 want=2,
  8 want=0 lines), with no encoding/Unicode/multiline/boundary cases and
  no real-world distribution. "Recall" and "precision" are loaded terms;
  a non-expert (or a screenshot) reads them as evaluated detector
  quality. The corpus header documents two by-design exceptions
  (`phone_bare10` expects 0 — a documented residual, not a miss;
  `clean_price` expects 2 — review-by-design), which is good, but only in
  corpus comments.
- **Recommendation:** Frame the F-card as a confusion-matrix-style
  fixture check ("36 hand-picked fixtures, not a sample of real attacks")
  with an explicit "what this does not measure" line, and add
  KNOWN-GAP markers naming the deliberately uncovered classes
  (encoding/obfuscation, Unicode/homoglyphs, multiline splits, boundary
  collisions) linked to the backlog. This is the measurement-rigor
  backlog item; it belongs at P0 of the backlog (see below).

### P1 — Contributor quickstart's shim-delegate step is the highest stuck risk in the funnel

- **Priority:** P1
- **Evidence:** `CONTRIBUTING.md` quickstart step 2 is a comment: "(In CI
  these are inert fakes; locally any second executable works — it is
  never invoked with real data in simulated mode.)" No script, no
  filename, no PATH-ordering warning. CI provisions delegates with
  `sudo tee /usr/local/bin/hatch_gws_cli` — not portable to a
  contributor's machine, and the audit's key invariant is that the shim
  must shadow a *distinct* executable ("a shim must never be 'tested'
  against itself"). A new contributor must invent this correctly or the
  "shim shadows real binary on PATH" checks fail with no troubleshooting
  guidance. The quickstart has no troubleshooting section at all.
- **Recommendation:** Ship a local equivalent (e.g.
  `test/stub-memory-skill/build/provision-delegates.sh` writing inert
  fakes to a documented dir), state the PATH-ordering requirement and
  its failure mode explicitly, and add a 5-line troubleshooting block
  (delegate missing / wrong PATH order / stale `local.env` in the repo
  dir — `local.env` is present but gitignored and CI refuses a committed
  one; the quickstart never mentions whether to source or delete it).

### P1 — "Expect CLEAN" overpromises what a contributor just proved

- **Priority:** P1
- **Evidence:** Quickstart: "`bin/leakage-audit          # expect
  CLEAN`". The only qualification lives in the separate "What CI green
  means" section. The next paragraph invites contributors to point
  `PERSONAL_MEMORY_SKILL` at their *own installation* — where "CLEAN"
  most risks being read as "my installation is protected," when the
  audit proves plumbing + fixed-corpus behavior, not real-world
  protection. Iteration 4 worked hard to make stub-green unmistakable
  (banner + title + hero + footer + live-fire refusal + CI grep for
  `SYNTHETIC STUB TARGET`); the contributor doc is the one place that
  diligence doesn't reach.
- **Recommendation:** One line under the quickstart commands: "CLEAN
  here means the harness is self-consistent against this target — it is
  not a verdict that any real installation is protected. See
  references/attack-surface.md §E for paths no audit can close." This
  keeps the stub-first promise (no private setup) without letting the
  funnel manufacture false confidence.

### P2 — By-design corpus exceptions are invisible in the report's per-case table

- **Priority:** P2
- **Evidence:** The corpus header documents `phone_bare10` (want 0, a
  documented residual — bare 10-digit numbers collide with confirmation
  numbers) and `clean_price` (want 2, review-by-design). The report's
  per-case table renders both as plain "want 0/2, got 0/2 ✓" rows with no
  annotation. A reader sees a phone-shaped value "passing" and concludes
  the detector handles it, when the truth is the opposite: it's a known
  hole. (Note the naming wrinkle: a case named `clean_price` counts
  toward "clean precision" vocabulary while expecting rc=2 — minor, but
  it muddies the metric story.)
- **Recommendation:** Annotate by-design rows in the table (e.g. a
  dagger linking to the corpus comment / the E-scenario), as the first
  KNOWN-GAP markers. Consider renaming `clean_price` to
  `price_review_by_design` so the name doesn't fight the metric.

### P2 — Suite-B fake binaries don't model real CLI behavior; the timeout path is untested

- **Priority:** P2
- **Evidence:** The red-team suite routes sends through inert fake real
  binaries (`exit 0`, `leakage-audit` lines ~315–330). Real CLIs can
  fail in ways fakes don't model: argv or payload echoed to stderr/logs,
  partial sends, slow responses. The audit wraps gate invocations in
  `timeout 30` (rc=124 handling present), but there is no corpus or
  red-team case exercising a slow/hung gate or a chatty real binary — the
  timeout path is dead code in practice. The blurbs say "the real binary
  uninvoked," proven only against a binary that does nothing.
- **Recommendation:** Backlog: add a deliberately slow fake gate and a
  chatty fake real binary (stderr echo) to prove timeout-fails-closed and
  no-evidence-leak, and document the fidelity boundary in
  `references/test-matrix.md`. This is the suite-B fidelity backlog item;
  P1 in the backlog (below) because it closes a "simulated transport"
  honesty gap, P2 as a standalone finding because the current simulated
  claim is at least explicit.

## What the report already gets right (PM view)

- The stub banner is a trust *strengthener*, not a diluter: "A 36/36 here
  proves harness self-consistency, not detector quality" (banner + title
  + hero + footer, CI-enforced via grep) is exactly the right posture for
  a trust instrument. It should be the model for the measurement-honesty
  fixes above.
- One-sentence callouts derived from the actual run pass the 30-second
  test for *status*; they fail it only for *semantics* (findings P0-1,
  P0-2).
- The "What CI green means" section in CONTRIBUTING is the right
  instinct; findings P1-5/P1-6 ask that it cover the local quickstart
  too, not just CI.
- `exit 3` (refuse to write an untrustworthy report) is the product's
  strongest honesty feature; the ⚪ "treat as unknown" card should match
  its severity visually.

## Iteration-5 backlog prioritization (P0 → P2, one-line rationale each)

1. **P0 — Measurement rigor (confusion-matrix framing, KNOWN-GAP
   markers):** the report is a trust instrument — every green number that
   can be read as detector quality is a potential overclaim, so honest
   framing is load-bearing, not polish. *(Covers findings P1-3, P1-4,
   P2-7.)*
2. **P0 — Residual-gap documentation:** the tracked residuals
   (absolute-path shim bypass, browser-task VM gap, mandate-only
   brief-gate, voice calls) are the actual remaining risk surface; users
   need actionable guidance per gap, not just names in a yellow card.
3. **P1 — Suite-B fake-binary fidelity and timeout coverage:** closes the
   "simulated transport" honesty gap — proving "real binary uninvoked"
   against a do-nothing binary is the weakest link in the red-team
   story. *(Covers finding P2-8.)*
4. **P1 — Adversarial encoding/Unicode/multiline/boundary expansion:**
   real attacks obfuscate; the 36-case ASCII single-line corpus is the
   largest known blind spot behind the "Detection performance" label.
5. **P2 — SHAPES manifest expansion:** incremental shape coverage with
   diminishing returns relative to the structural gaps above.
6. **P2 — a11y polish:** iterations 3–4 already shipped the substantive
   a11y work (native buttons, landmarks, visually-hidden status text,
   reduced-motion); what remains is refinement.
