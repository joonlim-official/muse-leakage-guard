"Iteration 4: CI readiness + synthetic stub skill".

What the repo is: a validation-only harness whose main human output is
a mobile-friendly HTML report (bin/leakage-report): per-suite callout
cards, expandable per-check evidence, an adversarial per-case table, and
raw transcripts in collapsible sections. Iteration 4 added: a real
accessible "match" table header, visually hidden matched/mismatched
labels, visually hidden Pass/Fail/Skipped text on evidence rows, and a
stub banner. Reports land in hidden_files/reports/ (gitignored).

Your task: review from the accessibility-specialist perspective and
produce a findings list (each: priority, title, evidence, recommendation,
WCAG criterion where applicable).

Focus for iteration 5:
- Generate a stub-target report and audit it hands-on: keyboard
  navigation (all expandables operable, visible focus), screen-reader
  traversal order (headless check of the DOM order vs visual order),
  heading hierarchy (exactly one h1, logical nesting), and the table
  semantics of the adversarial per-case table.
- Color independence: the green/yellow/red/blue verdict language must
  not rely on color alone — verify the text labels carry the meaning
  everywhere (badges, cards, table cells, the stub banner) and flag any
  color-only signal.
- The visually hidden (.vh) text added in iteration 4: verify it is
  actually exposed to assistive tech (not display:none) and that it
  reads sensibly in context ("matched", "Pass:").
- Reduced-motion and zoom: check for animations/transitions that need
  prefers-reduced-motion handling, and verify the report remains usable
  at 200% zoom / 320px width without horizontal scrolling or clipped
  content.
